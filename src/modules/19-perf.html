Making hardware faster means either finishing each task sooner or finishing more tasks per unit time. The two are different, they are improved by different techniques, and confusing them is one of the most common mistakes in performance reasoning. This module builds the quantitative tools first and then applies them to the most important performance technique in hardware: pipelining.

Latency and throughput

The time from the start of one task to its completion, for example the time to execute one instruction or to fetch one cache line. The number of tasks completed per unit time, for example instructions per second or bytes per second.

A fighter jet carries one person at 2,400 km/h; a large airliner carries 400 people at 900 km/h. The jet has lower latency for a single traveler; the airliner moves 360,000 person-kilometers per hour against the jet's 2,400, so it has 150 times the throughput. Caches primarily reduce latency (); pipelining and parallelism primarily raise throughput, and can even increase the latency of each individual task.

The processor performance equation

The time a program takes on a processor factors into three terms:

execution time = instruction count × CPI × clock period = IC × CPI / f

CPI is the average number of clock cycles per instruction. Each factor is controlled by different decisions: the instruction count by the ISA and compiler, CPI by the microarchitecture (pipelining, caches, branch prediction) and the instruction mix, and the clock period by the circuit design and process technology (). The factors interact, which is why a single number such as clock frequency, or instructions per second without regard to what the instructions do, is a poor measure of performance. A deeper pipeline raises f but usually raises CPI too; a richer ISA lowers the instruction count but may lengthen the cycle.

Speedup compares two systems running the same work: speedup = timeold/timenew.

Amdahl's law

If an improvement speeds up only part of a task, the rest limits the overall gain. If a fraction p of the original time is accelerated by a factor s and the remaining 1 − p is unchanged:

speedup = 1 / ((1 − p) + p/s) ≤ 1/(1 − p) as s → ∞

A program that is 90% parallelizable can never run more than 10 times faster on any number of processors; on 16 processors it reaches 1/(0.1 + 0.9/16) = 6.4. Amdahl's law tells you where to spend design effort: on the part that dominates the remaining time.

Gustafson's law describes the opposite situation, where the problem grows with the machine: if the parallel part scales with N processors while the serial part stays fixed, the scaled speedup is (1 − p) + p·N. Amdahl's law describes strong scaling (fixed problem size), Gustafson's weak scaling (fixed time per processor), and both are needed to reason about GPUs and clusters ().

Pipelining

Suppose a block of combinational logic takes 10 ns, and we must process a stream of 100 inputs, for example computing C[i] = (A[i] + B[i])/4. Without pipelining, each input must pass all the way through before the next can enter: 100 × 10 ns = 1000 ns. Inserting a register halfway through the logic splits it into two stages of 5 ns each. Now a new input can enter every 5 ns, while the previous input is in the second stage.

Pipelining inserts registers into a long combinational path. Each stage works on a different input at the same time.

With k equal stages of delay Ts, the first result appears after k·Ts (the pipeline fills) and then one result emerges every Ts, so N inputs take (k + N − 1)·Ts:

Stages | Stage time | Time for 100 inputs | Speedup 1 | 10 ns | 1000 ns | 1.0 2 | 5 ns | (2 + 99) × 5 = 505 ns | 1.98 4 | 2.5 ns | (4 + 99) × 2.5 = 257.5 ns | 3.88

For long streams the speedup approaches k. The latency of each individual input did not improve: it still spends 10 ns in the logic. Three effects limit how far pipelining can go:

  • Register overhead. Each stage pays tclk→Q + tsetup (plus skew margin). If the logic takes T and the overhead is treg, the stage time is T/k + treg, so throughput can never exceed 1/treg and returns diminish as k grows.
  • Balance. The clock is set by the slowest stage, so an unbalanced split wastes time in every other stage.
  • Dependencies. Pipelining helps only if inputs are independent. When one input needs the result of the previous one, it must wait, as the next sections show.

The registers are essential, not incidental: without them, fast signals for the next input would catch up with slow signals for the current one somewhere inside the logic, mixing two computations (this is exactly the race of ).

The instruction pipeline

A processor applies the same idea to the instruction cycle. The classic RISC pipeline has five stages, matching the steps of : instruction fetch (IF), decode and register read (ID), execute (EX), memory access (MEM) and write back (WB). Each stage takes one cycle, and a new instruction can start every cycle, so the ideal CPI is 1 even though each instruction takes five cycles.

Pipeline registers between the stages carry each instruction's values and control signals along with it. The forwarding paths are explained below.

The ideal is broken by hazards, situations in which the next instruction cannot proceed in the next cycle:

  • Structural hazards: two instructions need the same hardware in the same cycle, for example one memory for both instruction fetch and data access. Separate instruction and data caches remove the most common case.
  • Data hazards: an instruction needs a result that an earlier instruction has not yet written back.
  • Control hazards: the processor does not know which instruction to fetch next until a branch is resolved.

Data hazards and forwarding

In add x1, x2, x3 followed by sub x4, x1, x5, the sub reads x1 in ID one cycle after the add was there, but the add writes x1 only in WB, three cycles later. Stalling until the write completes would cost several cycles per dependency. But the add's result already exists at the end of its EX stage, sitting in the EX/MEM pipeline register. Forwarding (bypassing) adds multiplexers at the ALU inputs that select a value from the EX/MEM or MEM/WB register instead of the register file whenever a hazard-detection unit sees that an older instruction in flight writes the register being read. With forwarding, back-to-back dependent ALU instructions run without stalls.

A load is different: its value is not available until the end of MEM, too late to forward to an instruction in EX in the very next cycle. A dependent instruction immediately after a load must stall one cycle (a load-use hazard): the hazard unit holds the PC and the IF/ID register and injects a bubble (a no-op) into EX. Compilers reduce these stalls by scheduling an independent instruction between the load and its use.

Control hazards and branch prediction

A conditional branch is resolved (taken or not, and where to) in EX in the simple pipeline, two cycles after it was fetched. Meanwhile the processor has already fetched the next two instructions. If it simply guesses "not taken" and continues sequentially, it wins whenever the branch falls through and must flush the two wrong-path instructions otherwise: a 2-cycle penalty per taken branch. Because about one instruction in five is a branch, and modern pipelines resolve branches 10 to 20 cycles after fetch, this cost would be enormous without branch prediction.

  • Static prediction uses a fixed rule, such as predicting backward branches (loops) taken and forward branches not taken.
  • Dynamic prediction learns from history. The basic element is a 2-bit saturating counter per branch (indexed by bits of the branch's address): it predicts taken in its two upper states, and it takes two consecutive mispredictions to change the prediction, so a loop's single exit does not flip the guess for the next run of the loop.
  • A branch target buffer caches the target addresses of taken branches so that fetch can redirect in the very next cycle. Modern predictors combine global and local history and achieve accuracies well above 95%.
The 2-bit saturating counter. A 1-bit predictor (remember the last outcome) mispredicts twice per loop execution: at the exit and again at the start of the next run.

Stalls simply add to the CPI: CPI = 1 + (stall cycles per instruction), summed over every hazard type. For example, if 25% of instructions are loads and 40% of them are followed immediately by a dependent instruction (1 stall), and 15% are branches mispredicted 30% of the time with a 2-cycle penalty, CPI = 1 + 0.25 × 0.4 × 1 + 0.15 × 0.3 × 2 = 1.19.

Beyond the simple pipeline

High-performance processors extract more instruction-level parallelism (ILP) with several techniques built on the same foundations:

  • Superscalar issue fetches, decodes and executes several instructions per cycle (4 to 8 in current designs), with multiple ALUs and more register file ports, so CPI can fall below 1 (often quoted as IPC, instructions per cycle, above 1).
  • Out-of-order execution lets later independent instructions run while an earlier one waits for a cache miss. Instructions wait in a scheduling window until their operands are ready. Register renaming maps the architectural registers onto a larger pool of physical registers, eliminating false dependencies (write-after-read and write-after-write) that come only from reusing register names. A reorder buffer retires instructions in program order, so exceptions remain precise and the program cannot observe the reordering.
  • Speculation executes past predicted branches and discards the results if the prediction was wrong.
  • Simultaneous multithreading (SMT) lets two or more threads share one core's execution units to fill slots that a single thread leaves idle.

These techniques cost large amounts of area and power for diminishing gains, because real programs have limited ILP. Combined with the end of voltage scaling (), this pushed the industry toward many simpler cores and massively parallel processors such as GPUs ().

Summary

  • Latency is time per task; throughput is tasks per time. Pipelines raise throughput, not latency.
  • Time = IC × CPI × T. Speedup = old time/new time.
  • Amdahl: speedup = 1/((1 − p) + p/s) ≤ 1/(1 − p). Gustafson (scaled): (1 − p) + pN.
  • k-stage pipeline: N items take (k + N − 1)Ts; stage time T/k + treg; balance matters.
  • Hazards: structural, data (forwarding removes most; load-use costs a stall), control (prediction; 2-bit counters, BTB).
  • CPI = 1 + Σ(frequency × penalty) over stall sources. Superscalar, out-of-order execution, renaming and speculation go beyond CPI = 1 at a high cost in power.

A program executes 2 × 10⁹ instructions with an average CPI of 1.5 on a 3 GHz processor. How long does it take?

2 × 10⁹ × 1.5 / (3 × 10⁹) = 1.0 s.

80% of a program's time is spent in a function you make 4 times faster. What is the overall speedup? What is the maximum possible speedup from optimizing that function?

1/(0.2 + 0.8/4) = 1/0.4 = 2.5. Maximum (function takes no time): 1/0.2 = 5.

A 10 ns block is split into a 5-stage pipeline of 2 ns stages (ignore register overhead). How long do 1000 inputs take, unpipelined and pipelined?

Unpipelined: 1000 × 10 = 10,000 ns. Pipelined: (5 + 999) × 2 = 2008 ns, a speedup of 4.98.

A program has 25% serial work. What speedup does it get on 8 cores, and what is the limit with unlimited cores?

1/(0.25 + 0.75/8) = 1/0.34375 = 2.91. Limit: 1/0.25 = 4.

Processor A runs at 4 GHz with CPI 2.0; processor B runs at 3 GHz with CPI 1.2 on the same program (same instruction count). Which is faster, and by how much?

Time per instruction: A = 2.0/4 = 0.5 ns, B = 1.2/3 = 0.4 ns. B is 1.25 times faster despite its lower clock frequency.

Logic of 8 ns is pipelined with a register overhead of 0.5 ns per stage. Compute the clock period and throughput speedup (relative to one stage) for 1, 4, 8 and 16 stages.

T = 8/k + 0.5. k = 1: 8.5 ns (1.0). k = 4: 2.5 ns (3.4×). k = 8: 1.5 ns (5.7×). k = 16: 1.0 ns (8.5×). Doubling the stages from 8 to 16 gives only 1.5× more, and no number of stages can beat 1/0.5 ns = 2 GHz.

In a 5-stage pipeline with full forwarding and a one-cycle load-use stall, how many stall cycles does this sequence incur?

lw   x1, 0(x2)
add  x3, x1, x4
sub  x5, x3, x6
lw   x7, 4(x2)
and  x8, x5, x9
or   x10, x7, x8

add uses x1 right after the load: 1 stall. sub uses x3 from add: forwarded, no stall. and uses x5 from sub (two instructions back): forwarded, no stall; it does not use x7. or uses x7 from the second load, which is two instructions back: by then the load has finished MEM, so it is forwarded from MEM/WB, no stall. Total: 1 stall cycle. (Swapping the second lw above sub would not remove the first stall; moving it between the first lw and add would.)

Compute the CPI for a pipeline with base CPI 1 where 30% of instructions are loads, half of which have a dependent instruction immediately after (1 stall), and 20% are branches, predicted with 90% accuracy and a 3-cycle misprediction penalty.

CPI = 1 + 0.30 × 0.5 × 1 + 0.20 × 0.10 × 3 = 1 + 0.15 + 0.06 = 1.21.

A loop branch is taken 9 times and then not taken once, and the loop runs many times. What is the steady-state accuracy of a 1-bit predictor (predict the last outcome) and of a 2-bit saturating counter?

1-bit: it mispredicts the exit (predicting taken) and then the first iteration of the next run (predicting not taken, the last outcome): 2 misses per 10, 80%. 2-bit: the exit moves the counter from strongly to weakly taken, so the next run's first iteration is still predicted taken: 1 miss per 10, 90%.

Using Gustafson's law, what scaled speedup does a workload with a 5% serial fraction achieve on 64 processors? Compare with Amdahl's prediction for the same fraction.

Gustafson: 0.05 + 0.95 × 64 = 60.85. Amdahl (fixed problem size): 1/(0.05 + 0.95/64) ≈ 15.4. The difference is the assumption: Gustafson grows the problem so that the parallel part dominates.

Design A is a 5-stage pipeline at 1 GHz with a 2-cycle branch misprediction penalty. Design B is a 10-stage pipeline at 1.8 GHz with a 5-cycle penalty. With 20% branches and a 10% misprediction rate (and no other stalls), which is faster and by how much?

A: CPI = 1 + 0.2 × 0.1 × 2 = 1.04 → 1.04 ns per instruction. B: CPI = 1 + 0.2 × 0.1 × 5 = 1.10 → 1.10/1.8 = 0.611 ns. B is 1.70 times faster. With a worse predictor (say 30% mispredictions) B's CPI would be 1.30 → 0.72 ns, still faster but by less: deeper pipelines need better prediction.

Identify every true (read-after-write), anti (write-after-read) and output (write-after-write) dependence in this code, and say which ones register renaming removes.

div  x1, x2, x3
add  x4, x1, x5
sub  x1, x6, x7
mul  x8, x1, x4

RAW: add reads x1 from div; mul reads x1 from sub and x4 from add. WAR: sub writes x1, which add reads (sub must not overwrite x1 before add has read it). WAW: div and sub both write x1. Renaming gives sub's x1 a new physical register, which removes the WAR and WAW dependences, so sub can execute immediately instead of waiting behind the slow div and add. The RAW dependences are real data flow and remain.

Why does pipelining increase the latency of an individual operation slightly, and why do designers accept that?

Each stage adds register overhead (tclk→Q + tsetup), and the clock is set by the slowest stage, so an operation spends k × Tstage ≥ Tlogic + k·treg in the pipeline. Designers accept it because the goal is throughput over long streams of independent operations (instructions, pixels, packets), where the rate of one result per cycle dominates. When an operation's result is needed immediately by the next (dependencies), latency matters again, which is why forwarding and short critical loops (ALU to ALU, load to use) get so much attention.
