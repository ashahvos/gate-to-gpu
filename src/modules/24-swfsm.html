The button program in works, but it cannot do anything else while it waits for the button to be released. Real embedded programs juggle several activities at once: blinking an indicator, scanning a keypad, updating a display, watching a sensor. Without an operating system, the standard way to do that is to write each activity as a state machine that does a small amount of work and returns, and to step all of them from one loop. The state machine model is exactly the one from ; only the implementation changes from flip-flops to variables.

State in software

The state of a program is whatever it must remember to interpret its next inputs. A play/pause button needs one bit (playing or paused) to know what a press means. In hardware that bit lives in a flip-flop; in software it lives in a variable. A state diagram is drawn the same way in both cases, with Moore outputs inside states and Mealy outputs on transitions, written as condition / action.

A washing machine controller. FULL, EMPTY, LID and PAID are sensor inputs, T is a timer, and N counts remaining rinse cycles. The actions after the slashes happen once, on the transition.

Every time step of a state machine, in hardware or software, does the same three things: read the inputs, use the current state and the inputs to determine the outputs and the next state, and move to the next state.

The structure of the program

One loop iteration is one time step. The single delay at the end sets the time step for everything.
  • Keep the state in a variable, and name the states with an enum.
  • Run a while (1) loop with exactly one delay per iteration (or, better, wait for a timer tick; see ). That makes every iteration one time step of known length.
  • Read each input once per iteration into a local variable, so that every decision in the iteration sees the same value.
  • Use a switch (or if-else chain) on the current state; inside each case, check the inputs, set the next state and perform the transition actions.
  • Never wait inside a case. A state that needs to wait simply stays in the same state on the next iteration.

Example: debouncing without blocking

Debouncing is a natural state machine: the program must remember whether the button is up or down and whether it has been stable long enough. Sampling once per millisecond and requiring five consecutive identical samples gives a 5 ms debounce that never blocks.

The debouncer. The action that responds to a press belongs on the transition from MAYBE DOWN to PRESSED, so it runs exactly once per press. 
enum state { RELEASED, MAYBE_DOWN, PRESSED, MAYBE_UP };

int main(void)
{
    enum state s = RELEASED;
    uint8_t count = 0;
    DDRB |= (1 << PB5);                            // LED output
    PORTD |= (1 << PD2);                           // button input with pull-up

    while (1) {
        uint8_t down = (PIND & (1 << PD2)) == 0;   // read the input once

        switch (s) {
        case RELEASED:
            if (down) { s = MAYBE_DOWN; count = 0; }
            break;
        case MAYBE_DOWN:
            if (!down)
                s = RELEASED;                      // it was a bounce
            else if (++count == 5) {
                s = PRESSED;
                PORTB ^= (1 << PB5);               // Mealy action: once per press
            }
            break;
        case PRESSED:
            if (!down) { s = MAYBE_UP; count = 0; }
            break;
        case MAYBE_UP:
            if (down)
                s = PRESSED;
            else if (++count == 5)
                s = RELEASED;
            break;
        }
        /* other tasks go here, each taking a short step */
        _delay_ms(1);                              // one time step
    }
}

The distinction between Moore and Mealy outputs matters in software too. Code placed in a state's case runs on every iteration spent in that state (a Moore output, like keeping a motor on); code placed on a transition runs once (a Mealy action, like counting a press). Toggling the LED inside case PRESSED would toggle it every millisecond while the button is held.

Time-based transitions

With a fixed time step, time is measured by counting iterations. A traffic light with a 1-second loop that must stay green for 30 s, yellow for 5 s and red for 35 s keeps a counter, resets it on every transition, and leaves each state when the counter reaches that state's duration. Transitions that always happen when time runs out are drawn with the label "1" (unconditional) or with the timer condition.

enum light { GREEN, YELLOW, RED };
enum light s = GREEN;
uint8_t t = 0;                       // seconds spent in the current state

while (1) {
    t++;
    switch (s) {
    case GREEN:  if (t == 30) { s = YELLOW; t = 0; } break;
    case YELLOW: if (t == 5)  { s = RED;    t = 0; } break;
    case RED:    if (t == 35) { s = GREEN;  t = 0; } break;
    }
    set_lamps(s);                    // Moore outputs: a function of the state only
    _delay_ms(1000);
}

Several tasks at different rates

A program that must blink an LED every 250 ms and also scan buttons every 100 ms cannot simply delay 250 ms or 100 ms. Instead, choose a base tick that divides every task's period, the greatest common divisor: GCD(250, 100) = 50 ms. Each task keeps its own counter and runs every k ticks.

uint8_t blink_ticks = 0, scan_ticks = 0;
while (1) {
    if (++blink_ticks == 5) { blink_ticks = 0; PORTD ^= (1 << PD7); }   // every 250 ms
    if (++scan_ticks == 2)  { scan_ticks = 0;  scan_buttons(); }        // every 100 ms
    _delay_ms(50);                                                      // the base tick
}
Two tasks on a 50 ms base tick. A single shared counter would instead wrap at the least common multiple of the periods (500 ms = 10 ticks) and test the counter modulo each task's tick count.

This structure, often called a superloop with cooperative multitasking, is how a great deal of firmware is written. Its rule is that no task may block: each one does a little work and returns, so that every task is serviced every tick. A task that needs to wait for something keeps a state that says so and checks again next tick. Getting stuck in a long loop or a long delay inside one task (tunnel vision) starves all the others.

The delay-based tick has a weakness: each iteration takes the delay plus however long the tasks ran, so the timing drifts as the program grows. Driving the loop from a hardware timer interrupt fixes that ().

State machines for recognizing strings

Searching a stream of characters for a pattern is another state machine problem, the software twin of the hardware sequence detectors in . A naive search compares the pattern at every starting position, re-reading characters, which costs O(N·T) for text length N and pattern length T. A finite automaton whose state is "how many characters of the pattern currently match" reads each character exactly once, O(N), using the same longest-suffix-that-is-a-prefix rule to decide where to go on a mismatch (this is the Knuth–Morris–Pratt algorithm). The Aho–Corasick algorithm extends the idea to many patterns at once, as needed for searching text for a set of keywords.

Summary

  • State is what must be remembered; in software it is a variable, usually an enum.
  • Loop structure: read inputs once, switch on the state to choose outputs and the next state, then wait one tick.
  • Code in a state runs every tick (Moore); code on a transition runs once (Mealy).
  • Count ticks for time-based transitions; reset the count on every transition.
  • Multiple rates: base tick = GCD of the periods, one counter per task; never block.
  • Pattern matching with an automaton reads each input once: O(N) instead of O(N·T).

How many states does the controller of a single play/pause button need, and what is the output in each?

Two: PAUSED (output: stopped) and PLAYING (output: playing). Each debounced press moves to the other state.

Tasks must run every 250 ms and every 100 ms. What base tick should the loop use, and after how many ticks does the combined pattern repeat?

GCD(250, 100) = 50 ms. The pattern repeats after LCM(250, 100) = 500 ms = 10 ticks.

Why should a software state machine read each input once per iteration into a variable instead of reading the port register in every if?

The pin can change between two reads, so different tests in the same iteration could see different values: for example, one branch sees "pressed" and moves to a new state while another sees "released" and performs a release action. Reading once makes the iteration a consistent snapshot, exactly as a clocked hardware machine samples its inputs at one edge.

An LED must blink at 2 Hz (one full on-off cycle every 500 ms). How often must the program toggle it, and what statement does the toggle?

Toggle every 250 ms. For an LED on PD7: PORTD ^= (1 << PD7);.

The traffic light loop runs once per second. How many iterations long is one complete cycle, and what happens if each iteration's task code takes 20 ms in addition to the 1-second delay?

30 + 5 + 35 = 70 iterations. With 20 ms of work per iteration each cycle takes 70 × 1.02 = 71.4 s instead of 70 s: the timing drifts by 2% and keeps drifting. A timer-driven tick removes the error.

Write the software state machine for a detector whose output is 1 after two or more consecutive 1s on an input sampled once per tick (states S0, S1, S2 as in ).

 
enum st { S0, S1, S2 };
enum st s = S0;
while (1) {
    uint8_t x = read_input();
    switch (s) {
    case S0: s = x ? S1 : S0; break;
    case S1: s = x ? S2 : S0; break;
    case S2: s = x ? S2 : S0; break;
    }
    write_output(s == S2);      // Moore output
    wait_tick();
}

Equivalently the state can be a saturating count of consecutive 1s: count = x ? min(count + 1, 2) : 0; with output count == 2; the count variable is the state.

Tasks must run every 30 ms and every 45 ms. Give the base tick, the tick counts for each task, and the length of the repeating schedule.

GCD(30, 45) = 15 ms. Task A every 2 ticks, task B every 3 ticks. LCM(30, 45) = 90 ms = 6 ticks.

The debouncer samples once per millisecond. The input (1 = down) reads 1, 0, 1, 1, 1, 1, 1, 1 after starting in RELEASED. On which sample is the press recognized?

Sample 1 (down): → MAYBE_DOWN, count 0. Sample 2 (up): → RELEASED (a bounce). Sample 3 (down): → MAYBE_DOWN, count 0. Samples 4–8 (down) increment count to 1, 2, 3, 4, 5; at sample 8 count reaches 5 and the machine enters PRESSED, toggling the LED once.

In the washing machine, the rinse counter N is decremented "on the transition from DRAIN to FILL". What goes wrong if a programmer instead writes N-- inside case DRAIN:?

Code inside a state runs on every iteration spent in that state. Draining takes many ticks, so N would be decremented once per tick rather than once per cycle, running out (or wrapping around, if N is unsigned) almost immediately. Actions that must happen once belong on transitions.

What is wrong with this task in a superloop, and how would you restructure it?

void beep_task(void) {
    if (alarm) {
        for (int k = 0; k < 500; k++) { PORTB ^= (1 << PB1); _delay_us(500); }
    }
}

The loop blocks for 500 × 0.5 ms = 250 ms, during which no other task runs (buttons are missed, displays freeze). Restructure as a state machine: keep a counter of remaining half-periods; on each tick (or in a timer interrupt at 2 kHz) toggle the pin once and decrement, and stop when the count reaches 0. Better still, generate the tone with a hardware timer in PWM or CTC toggle mode ().

Design a thermostat state machine with states OFF, HEAT and COOL, a temperature input T and a setpoint S. Heating starts below S − 1 and stops at S; cooling starts above S + 1 and stops at S. Give the transitions and explain the role of the 1-degree band.

OFF → HEAT when T < S − 1; OFF → COOL when T > S + 1; otherwise stay OFF. HEAT → OFF when T ≥ S; else stay. COOL → OFF when T ≤ S; else stay. The gap between the start and stop thresholds is hysteresis: without it, measurement noise around S would switch the heater on and off rapidly, wearing out relays and wasting energy. The state remembers which way the system was heading, which a function of T alone cannot do.

Build the string-matching automaton for the pattern "abab" over the alphabet {a, b}: states 0–4 (characters matched), with state 4 meaning a match. Give the transitions, assuming overlapping matches are reported.

0: a → 1, b → 0. 1 ("a"): a → 1, b → 2. 2 ("ab"): a → 3, b → 0. 3 ("aba"): a → 1, b → 4 (match). 4 ("abab"): a → 3 (the text ends in "aba"), b → 0. Each character causes exactly one transition, so a text of N characters is scanned in O(N), whereas checking every starting position separately can take O(N·T).

A program uses the 50 ms superloop. A new display task takes 70 ms to redraw the screen. What happens to the other tasks, and how can the display task be made to fit?

Every iteration in which the display runs takes over 120 ms instead of 50, so the 250 ms and 100 ms tasks run late and timing becomes irregular. Split the redraw into pieces that each fit comfortably in a tick (for example, one line of the display per tick, keeping the next line number as the task's state), or move it to a lower-priority background slot that runs only with leftover time. Measuring each task's worst-case execution time is part of designing such a system.
