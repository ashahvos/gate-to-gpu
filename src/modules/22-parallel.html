For thirty years single-thread performance improved by roughly 50% per year, from faster clocks and smarter pipelines. Around 2005 that curve flattened: supply voltage stopped scaling, so higher clock frequencies meant unmanageable power density (), and programs ran out of instruction-level parallelism to exploit (). Transistor counts kept growing, so the extra transistors went into parallel hardware: more cores per chip, wider vector units, and massively parallel processors such as GPUs. This module covers how that hardware works and what it asks of the programmer.

Forms of parallelism

  • Instruction-level: overlapping independent instructions inside one core (pipelining, superscalar and out-of-order execution).
  • Data-level: applying the same operation to many data elements at once (SIMD vector units, GPUs).
  • Thread- or task-level: running independent instruction streams on separate cores (multicore processors, clusters).

Flynn's classic taxonomy names machines by their instruction and data streams: SISD (a simple uniprocessor), SIMD (one instruction applied to a vector of data), MIMD (independent cores, each with its own program counter) and the rarely used MISD. GPUs follow a hybrid that NVIDIA calls SIMT (single instruction, multiple threads): programs are written as independent threads, but the hardware executes them in groups that share one instruction stream.

Shared-memory multiprocessors and coherence

A multicore processor has several cores, each with private L1 and usually L2 caches, sharing a last-level cache and main memory. Because each private cache can hold its own copy of a line, a write by one core could leave stale copies in others. A cache coherence protocol prevents that by guaranteeing that all cores see a single, consistent order of writes to each location. The widely used MESI protocol tracks each line in each cache in one of four states:

State | Meaning | Local read | Local write | Another core reads | Another core writes M (Modified) | only valid copy, differs from memory | hit | hit | supply the data, write back, go to S | supply or write back, go to I E (Exclusive) | only copy, clean | hit | hit, go to M with no bus traffic | go to S | go to I S (Shared) | clean; other caches may also hold it | hit | invalidate other copies, go to M | stay S | go to I I (Invalid) | not present | miss; go to E if no other cache has it, else S | miss; read for ownership, go to M | — | —

Small systems implement coherence by snooping: every cache watches a shared bus or ring for other cores' requests. Large systems use a directory that records which caches hold each line, so invalidations go only where needed.

Coherence works on whole lines, which creates a performance trap. If two cores repeatedly write two different variables that happen to share a cache line, every write invalidates the other core's copy, and the line bounces between them at the cost of a coherence miss each time. This is false sharing.

False sharing. The variables are unrelated, but the hardware cannot tell, because it tracks ownership per line.

Synchronization and atomic operations

When threads share data, ordinary loads and stores are not enough. The statement counter++ is a load, an add and a store; if two threads interleave them, one increment can be lost. If two threads each increment a shared counter 1000 times without synchronization, the final value can be anything from 2 to 2000. Such a data race is a bug, and in C and C++ it is formally undefined behavior.

Hardware provides atomic read-modify-write instructions that perform a load and a store as one indivisible operation, with the coherence protocol holding the line exclusively in between: fetch-and-add, exchange, and compare-and-swap (CAS: write a new value only if the location still holds an expected value), or the load-linked/store-conditional pair on RISC architectures. Locks, semaphores and lock-free data structures are all built from these.

A second issue is ordering. Compilers and processors reorder independent memory operations for speed, so another core may observe one thread's writes in a different order than they were written. Languages expose this through a memory model. In C++, std::atomic operations are sequentially consistent by default, and the weaker release/acquire pair is enough for the most common pattern, handing data from one thread to another:

#include

int payload;                                      // ordinary data
std::atomic ready{false};

void producer() {
    payload = 42;                                 // 1. write the data
    ready.store(true, std::memory_order_release); // 2. publish: earlier writes become visible first
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) { }  // 3. wait for the flag
    assert(payload == 42);                        // 4. guaranteed to see the data
}

std::atomic counter{0};
void work() { for (int k = 0; k < 1000; ++k) counter.fetch_add(1); }  // no lost updates

volatile is not a synchronization mechanism between threads in C or C++: it prevents the compiler from removing or caching accesses, but it does not make them atomic and does not order them with respect to other memory operations or other cores. It is the right tool for memory-mapped device registers and for variables shared with interrupt handlers on a single-core microcontroller (); between threads, use atomics or locks.

SIMD vector units

A SIMD instruction operates on a short vector held in a wide register: with 256-bit AVX registers, one instruction adds eight pairs of 32-bit floats. Compilers vectorize simple loops automatically when iterations are independent and data is contiguous; intrinsics or annotations handle harder cases. SIMD exploits data parallelism within one core at low cost, since the control logic (fetch, decode, scheduling) is shared across all lanes.

GPUs: designed for throughput

A CPU core is built to make a single thread fast: large caches, branch prediction and out-of-order execution all reduce the latency of one instruction stream. A GPU makes the opposite trade. It spends its transistors on arithmetic units, thousands of them, and tolerates latency instead of avoiding it: each processor holds many threads at once, and when one group of threads waits for memory, the scheduler simply issues instructions from another group in the next cycle. With enough threads in flight, the arithmetic units stay busy even though each individual memory access takes hundreds of cycles.

A GPU consists of many streaming multiprocessors (SMs). Each SM has warp schedulers, a large register file (so that thousands of threads can keep their state on-chip and switching between them costs nothing), integer and floating-point lanes, specialized matrix units (tensor cores), load/store units, and an on-chip memory that serves as L1 cache and programmer-managed shared memory.

A simplified SM. A large GPU has on the order of a hundred SMs; NVIDIA's GA100 die, for example, has 128.

Threads are executed in warps of 32. All threads of a warp execute the same instruction at the same time, each on its own data and registers. When threads of one warp take different sides of a branch, the warp executes both paths one after the other, disabling the lanes that did not take each path. This branch divergence wastes lanes; code whose branches are uniform across each warp (for example, conditions that depend on the warp index rather than on individual thread data) avoids it.

Divergence inside a warp. Execution time is the sum of both paths, with idle lanes in each.

The CUDA programming model

A CUDA program runs on a host CPU and launches kernels, functions executed by many GPU threads in parallel. A launch creates a grid of thread blocks; each block contains up to 1024 threads that run on the same SM, can share that SM's shared memory, and can synchronize with each other. Blocks are independent: the hardware runs them in any order, on any SM, which is what lets the same program scale across GPUs of different sizes.

Each thread computes which data element it owns from its block and thread indices. 
__global__ void vadd(const float *a, const float *b, float *c, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // this thread's element
    if (i < n)                                       // the last block may be partly empty
        c[i] = a[i] + b[i];
}

// host side: one thread per element, 256 threads per block
int threads = 256;
int blocks  = (n + threads - 1) / threads;           // round up
vadd<<>>(d_a, d_b, d_c, n);

The arrays d_a, d_b and d_c live in the GPU's own DRAM (global memory), allocated with cudaMalloc and filled with cudaMemcpy across the PCIe or NVLink connection, or managed automatically with unified memory. Transfers between host and device are slow compared with GPU memory bandwidth, so efficient programs keep data on the GPU across many kernels.

Shared memory is fast on-chip storage visible to all threads of a block. The standard pattern is to load a tile of data from global memory into shared memory, synchronize, and then let every thread reuse it many times. A parallel sum (reduction) shows both shared memory and synchronization:

__global__ void block_sum(const float *in, float *out, int n)
{
    __shared__ float s[256];                         // one slot per thread of the block
    int tid = threadIdx.x;
    int i   = blockIdx.x * blockDim.x + tid;
    s[tid] = (i < n) ? in[i] : 0.0f;
    __syncthreads();                                 // all loads done before anyone reads s[]
    for (int stride = blockDim.x / 2; stride > 0; stride /= 2) {
        if (tid < stride)
            s[tid] += s[tid + stride];               // halve the number of partial sums
        __syncthreads();
    }
    if (tid == 0)
        out[blockIdx.x] = s[0];                      // one result per block
}

Each step halves the number of active threads, so a block of 256 sums its values in log₂ 256 = 8 steps rather than 255 sequential additions; a second kernel (or atomics) combines the per-block results.

Feeding the GPU: coalescing and occupancy

GPU memory performance depends on access patterns at the level of a warp. When the 32 threads of a warp access consecutive addresses, the hardware coalesces them into a few wide transactions; scattered or strided accesses need many transactions for the same amount of useful data.

Stride-1 accesses fill each memory transaction with useful data; a stride of 2 wastes half of every transaction.

This is why GPU code favors structure-of-arrays layouts (separate arrays of x, y and z) over arrays of structures when a kernel reads one field, the same advice as for CPU caches () but with a larger penalty.

Occupancy is the number of warps resident on an SM relative to its maximum. More resident warps give the scheduler more chances to hide latency. Occupancy is limited by whichever per-SM resource runs out first: registers (a kernel using many registers per thread allows fewer threads), shared memory per block, or the maximum number of blocks and threads per SM. Maximum occupancy is not always necessary, but too little leaves the SM idle while waiting for memory.

How much parallelism is enough? Little's law, a result from queueing theory, answers this. In any steady-state system, the average number of items inside equals the rate at which they arrive multiplied by the average time each one spends inside. Applied to a memory system, the amount of data that must be in flight (requested but not yet returned) to sustain a bandwidth B when each request takes latency L is the product of the two:

data in flight = bandwidth × latency

A GPU with 2 TB/s of bandwidth and a loaded memory latency of 500 ns needs 2 × 10¹² B/s × 500 × 10⁻⁹ s = 1 MB of requests outstanding at every moment. Spread over 100 SMs, that is 10 KB per SM, or 2500 four-byte loads. An SM holding its maximum of 2048 threads cannot reach that if each thread issues one 4-byte load and waits for it before issuing the next. Fast kernels therefore give each thread several independent loads in flight, by unrolling loops so that loads are issued before earlier results are used, or by using 8- and 16-byte vector loads (float2, float4). Occupancy is one way to supply concurrency, and instruction-level parallelism within each thread is the other. The same law limits CPUs: a core can track only a fixed number of outstanding cache misses, which caps the bandwidth a single thread can draw no matter how fast the memory is.

Shared memory has its own access rule. It is divided into 32 banks, each 4 bytes wide, with successive 4-byte words in successive banks: word w lives in bank w mod 32. Each bank delivers one word per cycle, so a warp's access completes in one pass only if its 32 threads touch 32 different banks, or read the same word, which is broadcast to all of them. When k threads access different words in the same bank, the hardware replays the access k times: a k-way bank conflict. Stride-1 access, s[tid], is conflict free. s[2*tid] places two threads in each even-numbered bank, a 2-way conflict. Reading down a column of a 32 × 32 tile, s[tid][c], places all 32 threads in bank c, a 32-way conflict, because every row is 32 words long and starts in bank 0. The standard fix is padding: declared as s[32][33], element (r, c) is word 33r + c, in bank (r + c) mod 32, so the 32 elements of any column fall in 32 different banks at the cost of 32 unused words.

Matrix engines and precision

Dense linear algebra, the core of neural-network training and inference, maps well onto GPUs because matrix multiplication performs many operations per byte loaded. Modern GPUs add tensor cores that compute small matrix products (for example a 4 × 4 × 4 multiply-accumulate) in one instruction, in reduced precisions such as FP16, BF16 or FP8 with FP32 accumulation. The formats of matter here: BF16 keeps FP32's exponent range with fewer mantissa bits, which suits training, while narrower formats double throughput again at the cost of precision.

The roofline model

Whether a kernel is limited by computation or by memory traffic depends on its arithmetic intensity: floating-point operations performed per byte moved to or from DRAM. Attainable performance is the lower of the processor's peak compute rate and its memory bandwidth multiplied by the intensity.

attainable FLOP/s = min( peak FLOP/s, memory bandwidth × arithmetic intensity ) A roofline for a GPU with 60 TFLOP/s of compute and 2 TB/s of memory bandwidth. Below 30 FLOP per byte, memory bandwidth is the limit.

Vector addition performs one addition per 12 bytes (two 4-byte loads and one 4-byte store), an intensity of 1/12: at 2 TB/s it can reach only about 0.17 TFLOP/s, under 0.3% of peak, no matter how it is written. A large matrix multiplication with good tiling reuses each loaded element many times, reaches high intensity, and runs near the compute peak. The roofline tells an engineer which optimization matters: for a memory-bound kernel, reduce or reuse data movement (tiling into shared memory, fusing kernels, smaller data types); for a compute-bound one, use better instructions (tensor cores) or fewer operations.

Summary

  • Power and ILP limits turned extra transistors into parallel hardware: multicore, SIMD and GPUs.
  • Coherence (MESI: Modified, Exclusive, Shared, Invalid) keeps private caches consistent per line; false sharing makes unrelated writes conflict.
  • Data races lose updates; use atomic read-modify-write operations or locks, and release/acquire ordering to publish data. volatile is not thread synchronization.
  • GPUs hide latency with massive multithreading; warps of 32 threads execute in lockstep (SIMT), and divergent branches serialize.
  • CUDA: kernels launch grids of blocks of threads; i = blockIdx.x·blockDim.x + threadIdx.x; shared memory and __syncthreads() enable cooperation within a block.
  • Coalesced, stride-1 access and adequate occupancy keep the memory system and the SMs busy.
  • Little's law: data in flight = bandwidth × latency. Hiding latency needs enough independent requests outstanding, from many warps, several loads per thread, or wider loads.
  • Shared memory has 32 four-byte banks; threads of a warp accessing different words in one bank serialize. Pad 2-D tiles (for example [32][33]) to make column access conflict free.
  • Roofline: performance = min(peak, bandwidth × intensity). Low-intensity kernels are memory bound.

How many blocks of 256 threads are needed for n = 1,000,000 elements? Why does the kernel need the test if (i < n)?

⌈1,000,000/256⌉ = 3907 blocks, which launch 1,000,192 threads. The last 192 threads have no element; without the bounds check they would read and write past the end of the arrays.

Core 0 reads a line that no cache holds, then writes it; then core 1 reads the same line. Give the MESI state of the line in each cache after each step.

Core 0 read: core 0 E. Core 0 write: core 0 M, with no bus traffic, because no other copy exists. Core 1 read: core 0 supplies the data and writes it back; both caches hold it in S.

What is the arithmetic intensity of single-precision vector addition c[i] = a[i] + b[i], and what performance can it reach on a GPU with 2 TB/s of memory bandwidth?

1 FLOP per 12 bytes: 1/12 FLOP/B. 2 × 10¹² B/s × 1/12 ≈ 167 GFLOP/s, a tiny fraction of the compute peak: the kernel is memory bound.

Two threads each execute counter++ 1000 times on a shared int with no synchronization. Explain how updates are lost, and show that the final value can be as low as 2. Give two correct fixes.

Each increment is load, add, store. If thread A loads the value, thread B performs several complete increments, and A then stores its stale value + 1, B's increments vanish. A worst case: A loads 0; B runs 999 increments (counter = 999); A stores 1; B loads 1; A runs its remaining 999 increments (counter = 1000); B stores 2. Final value 2. Fixes: std::atomic<int> with fetch_add, or protect the increment with a mutex (or give each thread its own counter and sum at the end, which is also fastest).

In a warp, threads with even threadIdx.x take the if path (cost 100 cycles) and odd ones take the else path (cost 60 cycles). How long does the warp take? What if the condition were (threadIdx.x / 32) % 2 == 0 instead?

Every warp contains both even and odd threads, so each warp executes both paths: 160 cycles, with half the lanes idle each time. With the warp-level condition, all threads in a warp agree: each warp takes 100 or 60 cycles, and no lanes are wasted.

An SM has 65,536 registers and supports at most 64 resident warps. A kernel uses 64 registers per thread. What is the maximum occupancy? What if it used 32 registers?

65,536/64 = 1024 threads = 32 warps → 50% occupancy. With 32 registers: 2048 threads = 64 warps → 100% (if no other limit applies). Reducing register use, for example by recomputing values, can raise occupancy, at the risk of spilling to slower memory.

On the GPU of the roofline figure (60 TFLOP/s, 2 TB/s), what performance does a kernel with intensity 8 FLOP/B reach, and what intensity is needed to become compute bound?

min(60, 2 × 8) = 16 TFLOP/s: memory bound. The ridge point is 60/2 = 30 FLOP/B; above it the kernel is limited by compute.

Multiplying two N × N single-precision matrices performs 2N³ operations and, with perfect reuse, moves 3N² values. What is its best-case arithmetic intensity, and is N = 4096 compute bound on the example GPU?

2N³/(3N² × 4 bytes) = N/6 FLOP/B. For N = 4096: about 683 FLOP/B, far above the ridge at 30, so a well-tiled implementation is compute bound. Without tiling, data is reloaded many times and the effective intensity, and performance, collapse.

A kernel reads only the x field of an array of struct { float x, y, z, w; }. Compared with a separate array of x values, how many times more memory traffic does each warp generate?

Consecutive threads read addresses 16 bytes apart, so the 32 x values of a warp are spread over 512 bytes instead of 128: about 4 times the traffic (and transactions), three quarters of it unused. Converting to a structure of arrays restores fully coalesced access.

A GPU has 3 TB/s of memory bandwidth, a loaded memory latency of 600 ns, and 132 SMs, each holding up to 2048 threads. How many bytes must each SM keep in flight to use the full bandwidth? How many independent 4-byte loads must each thread have outstanding at full occupancy?

Little's law: 3 × 10¹² B/s × 600 × 10⁻⁹ s = 1.8 MB in flight across the chip, or 1.8 MB/132 ≈ 13.6 KB per SM. Divided among 2048 threads that is about 6.7 bytes per thread, so each thread needs at least two independent 4-byte loads outstanding (or one 8-byte vector load). With fewer resident threads, each thread needs proportionally more.

A CPU core can track 12 outstanding cache misses, each for a 64-byte line, and memory latency is 80 ns. What is the most memory bandwidth one core can draw? Why can a single thread not saturate a memory system rated at 100 GB/s?

Bandwidth = data in flight/latency = 12 × 64 B/80 ns = 9.6 GB/s. The core runs out of miss-tracking entries (often called line fill buffers) long before the memory runs out of bandwidth; reaching 100 GB/s takes about ten cores' worth of outstanding misses. Hardware prefetchers help a single thread only by keeping those entries busy.

A transpose kernel loads a 32 × 32 tile into __shared__ float t[32][32] by rows and then reads it by columns: thread i of a warp reads t[i][c]. What bank conflict does the column read cause? Show that declaring t[32][33] removes it.

Element (i, c) of the unpadded tile is word 32i + c, in bank (32i + c) mod 32 = c for every i: all 32 threads hit one bank, a 32-way conflict, so the read takes 32 passes. With rows of 33 words, element (i, c) is word 33i + c, in bank (i + c) mod 32, which is different for each i = 0 … 31: no conflict. The row-wise load stays conflict free as well, since consecutive threads still access consecutive words.

In the producer/consumer example, suppose both atomic operations used memory_order_relaxed. What could go wrong, and why do release and acquire prevent it?

Relaxed atomics guarantee only that the flag itself is updated atomically; they impose no ordering on other memory operations. The compiler or hardware could make the store to ready visible before the store to payload, or the consumer could read payload before its read of ready completes, so the consumer may see ready == true and still read the old payload. A release store guarantees that all earlier writes by the producer become visible before the flag; an acquire load guarantees that later reads by the consumer happen after it. Together they create a happens-before relationship from the write of payload to its read.

A memory-bound kernel runs on a CPU with 100 GB/s of memory bandwidth and on a GPU with 2 TB/s. The GPU also has 30 times the CPU's peak FLOP rate. Estimate the speedup, and explain why the FLOP ratio is irrelevant here.

For a memory-bound kernel, time ≈ bytes moved/bandwidth, so the speedup is the bandwidth ratio: 2000/100 = about 20× (ignoring the cost of copying data to the GPU, which can erase the gain for a single short kernel). The FLOP ratio would matter only for compute-bound kernels to the right of both machines' ridge points.

The block_sum reduction uses if (tid < stride) with stride halving from 128. Why is this ordering better than the "interleaved" version that uses if (tid % (2*stride) == 0) with stride doubling from 1? Consider both divergence and shared-memory access.

With tid < stride, the active threads are always a contiguous range starting at 0, so whole warps are either fully active or fully idle: there is no divergence until fewer than 32 threads remain, and idle warps retire early. Consecutive threads also access consecutive shared-memory words, avoiding bank conflicts. The interleaved version leaves scattered threads active in every warp (divergence at every step) and accesses words with growing strides, which causes bank conflicts.
