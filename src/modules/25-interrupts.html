So far the processor has found out about events by checking for them: reading a button pin every loop iteration, or spinning in a delay loop to measure time. Checking is called polling, and it has two costs: the processor spends time checking things that have not happened, and anything that happens between checks waits. I/O events occur on a scale of milliseconds while instructions take tens of nanoseconds, so a processor that polls spends almost all its time asking "anything yet?". Interrupts reverse the responsibility: the device signals the processor when something happens, and the processor stops what it is doing just long enough to deal with it.

What happens when an interrupt occurs

An interrupt is one kind of exception: an event that diverts the processor from the normal flow of the program. Exceptions include hardware interrupts from devices (a pin changed, a timer expired, a byte arrived), error conditions detected by the processor itself (an illegal instruction, an invalid address, division by zero on processors that trap it), and deliberate traps such as system calls into an operating system. Hardware detects the event; software, in an interrupt service routine (ISR), handles it.

The life of an interrupt. On the AVR, the hardware saves only the program counter; the compiler-generated ISR prologue saves any registers the ISR uses.
  1. The device sets an interrupt flag in one of its registers.
  2. After finishing the current instruction (the fourth step of the instruction cycle in ), the processor checks for enabled, pending interrupts.
  3. If one is pending, it saves the return address on the stack, disables further interrupts by clearing the global interrupt-enable bit, and jumps to the address stored for that interrupt in the vector table.
  4. The ISR runs. Its reti (return from interrupt) instruction restores the program counter and re-enables interrupts, and the interrupted program continues exactly where it left off.

An ISR looks like a function but is not called by the program. It runs asynchronously, between any two instructions of the main code; it takes no arguments and returns no value. It communicates with the rest of the program only through global variables and hardware registers.

Interrupts on the AVR

The ATmega328P has over twenty interrupt sources, each with its own vector: external interrupts INT0 and INT1; pin-change interrupts for each port (PCINT0 for port B, PCINT1 for C, PCINT2 for D); timer compare-match and overflow interrupts; USART receive-complete and transmit interrupts; SPI and TWI transfer complete; ADC conversion complete; and others. In avr-gcc an ISR is written with the ISR() macro and the vector's name, such as ISR(TIMER1_COMPA_vect) or ISR(PCINT2_vect).

An interrupt is taken only when three things are true:

  • its local enable bit is set in the peripheral's interrupt mask register (for example OCIE1A in TIMSK1);
  • the global interrupt enable (the I bit in the status register) is set, with sei(); cli() clears it;
  • the event has occurred and set the interrupt flag (for example OCF1A in TIFR1). The flag is cleared automatically when the ISR starts.

Enabling an interrupt without defining its ISR sends the processor to a default handler, which on the AVR jumps to the reset vector: the program appears to restart at random. Every enabled interrupt needs an ISR.

A pin-change interrupt fires when any enabled pin of its port changes in either direction. It does not say which pin changed or which way, so the ISR reads the PIN register and compares it with the previous value:

#include 
#include 

volatile uint8_t button_changed = 0;

ISR(PCINT2_vect)                    // any enabled pin on port D changed
{
    button_changed = 1;             // just record the event; keep the ISR short
}

int main(void)
{
    PORTD  |= (1 << PD2);           // button input with pull-up
    PCMSK2 |= (1 << PCINT18);       // PD2 is pin-change source PCINT18
    PCICR  |= (1 << PCIE2);         // enable pin-change interrupts for port D
    sei();                          // global enable

    while (1) {
        if (button_changed) {
            button_changed = 0;
            /* read PIND, debounce, act */
        }
    }
}

Hardware timers

A timer is a counter (TCNT) clocked by the system clock divided by a prescaler N (1, 8, 64, 256 or 1024 on the AVR). It counts at a precisely known rate, independent of what the program is doing, which makes it far more accurate than counting loop iterations: a delay-based loop runs late by however long its other work took, while a timer does not drift.

In CTC (clear timer on compare) mode, the counter is compared with an output-compare register (OCR) on every count; on a match it sets the compare flag, optionally requests an interrupt, and resets to zero. The result is a periodic event with

period = (OCR + 1) × N / fclk ⇒ OCR = fclk × period / N − 1 A timer in CTC mode: one compare match, and one interrupt, per period.

With fclk = 16 MHz and prescaler N = 256, the timer counts at 62.5 kHz (16 μs per count). A 0.25 s period needs 0.25 × 62,500 = 15,625 counts, so OCR1A = 15,624. (Many examples use 15,625, which gives 0.250016 s, an error of 0.006%.) The 16-bit Timer1 is needed because the count exceeds 255.

void timer1_init(void)
{
    TCCR1B |= (1 << WGM12);         // CTC mode, TOP = OCR1A
    OCR1A   = 15624;                // 0.25 s at 16 MHz / 256
    TIMSK1 |= (1 << OCIE1A);        // enable the compare-match A interrupt
    TCCR1B |= (1 << CS12);          // prescaler 256: this starts the timer
}

volatile uint8_t tick = 0;
ISR(TIMER1_COMPA_vect) { tick = 1; }

The prescaler is chosen as the smallest one for which OCR fits in the timer's width, which gives the finest resolution.

Driving the superloop of from a timer replaces _delay_ms() with "wait until the tick flag is set, then clear it". Each iteration then starts exactly one period after the previous one, however long the tasks took, as long as they finish within the period.

PWM with timers

Timers also generate waveforms directly on output pins with no software involvement. In fast PWM mode the counter ramps from 0 to TOP and wraps; the output pin is set at the start of each period and cleared when the counter passes the compare value, so the duty cycle is set by the compare register:

Fast PWM. Changing OCR changes the duty cycle from the next period on.
  • 8-bit fast PWM: fPWM = fclk/(N × 256), duty = (OCR + 1)/256. With 16 MHz and N = 64, fPWM ≈ 977 Hz.
  • Phase-correct PWM counts up and then down, halving the frequency (fclk/(N × 510)) but producing pulses centered in each period, which motor drivers prefer.
  • A hobby servo wants a 50 Hz frame with a 1 to 2 ms pulse. Timer1 with TOP set by ICR1 provides it: with N = 8 the timer counts at 2 MHz, so TOP = 2 MHz/50 − 1 = 39,999 and a 1.5 ms pulse needs OCR1A = 2999.

PWM controls LED brightness, motor speed and heater power, and with a low-pass filter becomes a simple DAC ().

Writing correct ISRs

Interrupts introduce concurrency: the main program and the ISR share variables and hardware, and the ISR can run between any two instructions. Three rules prevent most bugs.

Keep ISRs short. While an AVR ISR runs, other interrupts are disabled and wait. Long ISRs delay other events and can lose them (a second event of the same kind only sets a flag that is already set). The usual idiom is for the ISR to do only what must happen immediately, set a flag or store a value, and let the main loop do the rest. Never write to a slow display or wait inside an ISR.

Declare shared variables volatile. Within one function, the compiler may keep a variable in a register and assume it cannot change behind its back. In

uint8_t flag = 0;            // missing volatile
ISR(TIMER1_COMPA_vect) { flag = 1; }
...
while (flag == 0) { }        //! may compile to an infinite loop

the compiler can load flag once, see that nothing in the loop changes it, and loop forever. volatile forces a fresh memory access every time the variable is read or written. It is required for every global shared between an ISR and other code (and for memory-mapped registers, which the AVR headers already declare volatile).

Protect multi-step accesses. An operation that takes several instructions can be interrupted in the middle. On an 8-bit processor, even reading a 16-bit variable takes two instructions. If an ISR increments a 16-bit counter from 0x00FF to 0x0100 between the main program's two byte reads, the main program can read the low byte 0xFF and then the new high byte 0x01, getting 0x01FF, a value the counter never held. Read-modify-write sequences such as x++ or PORTB |= 0x01 (load, OR, store) have the same problem when the ISR modifies the same variable or register. The fix is a critical section that disables interrupts for the few instructions involved:

#include 

volatile uint16_t ticks;            // incremented by a timer ISR

uint16_t read_ticks(void)
{
    uint16_t copy;
    ATOMIC_BLOCK(ATOMIC_RESTORESTATE) {   // disables interrupts, restores the previous state afterwards
        copy = ticks;
    }
    return copy;
}

ATOMIC_RESTORESTATE restores the interrupt-enable bit to what it was, rather than blindly re-enabling interrupts, so the block is safe even if called from code that already had interrupts disabled. Critical sections must be short, because they add to the latency of every interrupt.

Latency, priority and the watchdog

Interrupt latency, the time from the event to the first instruction of the ISR, is a few cycles plus the remainder of the current instruction plus any time interrupts are disabled, by another ISR or a critical section. When several interrupts are pending, the AVR serves them in a fixed priority order given by the vector table and does not nest ISRs unless the programmer re-enables interrupts inside one. Larger microcontrollers have interrupt controllers with programmable priorities and nesting, so an urgent interrupt can preempt a less urgent ISR.

A watchdog timer is a timer that resets the microcontroller if it ever expires. The program restarts it periodically ("kicks the dog") from its main loop; if a bug or a glitch hangs the program, the kicks stop and the watchdog forces a reset instead of leaving the system stuck.

Summary

  • Polling checks repeatedly; interrupts let the device notify the processor. ISRs run asynchronously, between any two instructions.
  • Taking an interrupt: finish the instruction, save the PC, disable interrupts, jump through the vector table; reti returns and re-enables.
  • AVR: local enable + global I bit (sei/cli) + flag. Every enabled interrupt needs an ISR.
  • Timers count prescaled clock cycles. CTC: period = (OCR + 1)·N/fclk. Fast PWM: f = fclk/(N·256), duty from OCR.
  • Keep ISRs short (set a flag); declare shared globals volatile; protect multi-byte and read-modify-write accesses with critical sections.

List the three conditions that must all hold for the Timer1 compare-match A interrupt to be taken.

The local enable OCIE1A in TIMSK1 is set; the global enable (I bit) is set with sei(); and the compare match has occurred, setting the flag OCF1A.

With a 16 MHz clock and a prescaler of 64, how fast does a timer count, and how long is one count?

16 MHz/64 = 250 kHz, so one count is 4 μs.

What OCR value gives a 1 ms CTC period at 16 MHz with prescaler 64? Does it fit in an 8-bit timer?

OCR = 16 × 10⁶ × 0.001/64 − 1 = 250 − 1 = 249, which fits in 8 bits (≤ 255), so Timer0 or Timer2 can generate it.

What is the longest CTC period Timer1 (16 bits) can produce at 16 MHz, and with which prescaler?

Prescaler 1024 and OCR = 65,535: 65,536 × 1024/16 × 10⁶ = 4.19 s. Longer intervals need a software counter of timer ticks.

Why does a delay-based superloop drift over time while a timer-driven one does not?

A delay loop's iteration time is the delay plus the time the tasks take, and that varies; the errors accumulate. A timer counts the clock continuously in hardware, and the ISR marks each period's start independently of how long the software took (provided the tasks finish within the period).

Explain why the loop while (flag == 0) { } can hang forever if flag is set by an ISR but not declared volatile, and why volatile fixes it.

The compiler sees no assignment to flag inside the loop or the function, so it may load it into a register once and test that register forever, or even replace the loop with an infinite loop. The ISR's write to memory is never re-read. volatile tells the compiler the value can change outside the visible code, so every read in the loop is a real memory load.

A timer ISR increments volatile uint16_t ticks. The main program reads it with a simple assignment while the value changes from 0x00FF to 0x0100. Which wrong value can it see, and how do you prevent it?

The 8-bit AVR reads the low byte and the high byte with separate instructions. If it reads the low byte (0xFF), then the ISR increments the counter, then it reads the high byte (0x01), the result is 0x01FF = 511, although the counter went from 255 to 256. Read it inside ATOMIC_BLOCK(ATOMIC_RESTORESTATE) (or between cli() and the previous state's restoration) so the ISR cannot run between the two byte reads.

Configure 8-bit fast PWM at 16 MHz with prescaler 8. What is the PWM frequency, and what OCR value gives a 25% duty cycle?

f = 16 × 10⁶/(8 × 256) = 7812.5 Hz. Duty = (OCR + 1)/256 = 0.25 → OCR = 63.

Set up Timer1 for a hobby servo: a 50 Hz frame with prescaler 8 at 16 MHz. What TOP value goes in ICR1, and what OCR1A values give 1.0 ms, 1.5 ms and 2.0 ms pulses?

The timer counts at 2 MHz (0.5 μs). TOP = 2 × 10⁶/50 − 1 = 39,999. Pulses: 1.0 ms = 2000 counts → OCR1A = 1999; 1.5 ms → 2999; 2.0 ms → 3999.

A pin-change interrupt is enabled for PD2 and PD3. Inside the ISR, how can the program determine which pin changed and in which direction?

Keep the previous value of PIND in a static (or global) variable. In the ISR: uint8_t now = PIND; uint8_t changed = now ^ prev; prev = now;. A 1 in bit 2 or 3 of changed marks a pin that changed; that bit of now gives its new level (1 = rose, 0 = fell).

The main program executes PORTB |= 0x01; (compiled as load, OR, store) while a timer ISR toggles bit 7 of PORTB. Describe the race, and give two fixes.

If the ISR runs after the main program loads PORTB but before it stores the result, the ISR's change to bit 7 is overwritten by the stale copy: the toggle is lost. Fixes: wrap the main program's read-modify-write in a critical section (disable interrupts briefly); or use operations that are atomic in hardware, such as single-bit sbi/cbi on low I/O registers or writing 1 to the PIN register to toggle one bit; or arrange for only one context to write that register.

A UART at 115,200 baud receives 10-bit frames back to back. How much time is there between received bytes, how many 16 MHz clock cycles is that, and what does it imply for the receive ISR and for critical sections elsewhere?

115,200/10 = 11,520 bytes/s → 86.8 μs per byte = about 1389 cycles. The hardware receive buffer holds very little, so the ISR must read each byte before the next one arrives; the ISR itself should take tens of cycles, and no other ISR or critical section may block interrupts for anything close to 1389 cycles, or bytes are lost (an overrun).

Why should an ISR not write to an LCD, and how should the program be structured instead?

Writing to the display takes tens of microseconds to milliseconds per character, and on the AVR other interrupts are blocked while the ISR runs, so timer ticks, received bytes and button events would be delayed or lost. The display code may also be interrupted halfway through a command by the main program's own display code, corrupting the protocol. The ISR should store the new value and set a flag; the main loop checks the flag and updates the display.
